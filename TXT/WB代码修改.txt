一、新增能力：现在能做到什么
--------------------------------------------------------------------------------

1. 前端页面（要求 1）
   - 访问 http://127.0.0.1:8000/ 直接打开单页应用，无需 Node、无需构建。
   - 登录 / 注册切换、JWT 存 localStorage、刷新自动续上登录态。
   - 左侧会话列表：新建、切换、删除；标题自动取第一句提问。
   - 右侧聊天区：SSE 打字机效果、工具调用过程提示（🔍 正在调用… / ✅ 已返回）。
   - 文件：web/index.html、web/style.css、web/app.js

2. SQLAlchemy + 用户体系（要求 2）
   - 全异步 ORM：database/base.py（async engine / async_sessionmaker / get_db）。
   - 三张表：users、chat_sessions、chat_messages（外键 + 级联删除）。
   - 注册、登录、当前用户接口：/auth/register、/auth/login、/auth/me。
   - 密码 PBKDF2-SHA256（26 万次迭代 + 随机盐），库里看不到明文。
   - 能做什么：多用户各自独立的会话空间；别人拿到你的 session_id 也查不到（404）。

3. JWT 鉴权（要求 3）
   - auth/tokens.py：HS256 签发 / 校验，带 exp、iat、sub、username。
   - auth/dependencies.py：get_current_user 依赖，路由签名里只写 CurrentUser 即可。
   - 所有 /sessions 与 /chat 接口强制登录，401 时返回 WWW-Authenticate: Bearer。
   - 能做什么：无状态登录，多实例部署不需要共享 session 存储。

4. 流式输出（要求 4）
   - POST /chat/stream 返回 text/event-stream。
   - 事件：meta / tool_start / tool_result / delta / done / error。
   - 前端 fetch + ReadableStream 逐块解析（EventSource 发不了 POST + Header）。
   - 能做什么：首字延迟从「整段生成完」降到「第一个 token」；
     工具调用过程对用户可见，长任务不再像卡死。

5. 代码分层（要求 5）
   旧 → 新 对照：

   app.py（全部路由）        → app.py（只装配）+ api/routers/{auth,session,chat}_router.py
   app.py 的异常处理器       → api/exceptions.py
   app.py 的日志中间件       → api/middleware.py（改成纯 ASGI）
   agent/session.py（pymysql）→ agent/store.py（SQLAlchemy）
   agent/agent.py 里的 prompt → agent/prompts.py
   agent/agent.py 里的工具执行 → agent/tools_runner.py
   agent/agent.py 里的全局单例 → agent/factory.py（按请求装配）
   tools/knowledge.py（检索）  → rag/{loader,splitter,embedder,bm25,hybrid,retriever}.py
   tools/text_splitter.py      → rag/splitter.py（原文件保留为兼容层）
   散落的 os.getenv           → config.py（唯一配置源）

   能做什么：改一个接口只动一个文件；换检索策略不动 Agent；换 prompt 不动逻辑。

6. 全异步（要求 6）
   - 路由：全部 async def。
   - 数据库：create_async_engine + aiosqlite（或 aiomysql）。
   - LLM：openai.AsyncOpenAI；agent.run / agent.stream 都是协程 / 异步生成器。
   - 工具：统一 async def；万一有同步工具，执行器用 asyncio.to_thread 兜住。
   - 向量编码：sentence-transformers 是同步 CPU 操作，
     用 asyncio.to_thread 丢线程池，避免卡住事件循环。
   - 能做什么：一个用户等模型返回时，其他用户照常被服务。

7. 混合检索 RAG（要求 7）
   - 稠密：bge-small-zh-v1.5，归一化后点积 = 余弦，取前 10。
   - 稀疏：自实现 BM25（k1=1.5, b=0.75），中文按连续汉字二元组切词，取前 10。
   - 融合：RRF（k=60），score = Σ 1/(k + rank)。
   - 门槛：余弦 ≥ 0.55 才算有证据；只靠关键词命中的，余弦至少要 0.45。
   - 输出：每条证据带 来源 / 语义相似度 / 命中方式（dense / sparse / both）。
   - 能做什么：专有名词、错误码这类「必须原样命中」的查询也能召回；
     实测「今天股市怎么样？」这类库外问题仍能正确返回空 → 拒答链路不被破坏。

--------------------------------------------------------------------------------
一、改了什么
--------------------------------------------------------------------------------

原行为：按空行切段，段落超过 300 字就 split_text 定长硬切。
新行为：三级递归降级 + 短块吸附 + 整句重叠。

1. rag/splitter.py（重写）
   - 新增 split_document(text, max_chars=300, overlap=50, min_chars=60)：
     文档级入口，替代原来的 split_by_paragraph（后者已删除）。
   - _split_paragraphs：按空行切段。
   - _attach_short_blocks：< min_chars 的段并入相邻段，标题不再独立成块。
   - _split_sentences：句子边界 = 中文标点后（排除连续标点）/ 英文句点+空白 / 换行。
   - _split_long_sentence：单句仍超长时按逗号顿号冒号分句。
   - _split_tokens：最后一级兜底，英文按整词、中文按单字，超长单词硬切。
   - _merge_units：把短句攒到接近 max_chars，回退时按整句做重叠。
   - 保留 split_text（定长窗口），它现在是最后一级的底层工具。
   - 去掉"按内容全局去重"：重复出现的表格行/固定条款会被误删。

2. rag/loader.py
   - 改用 split_document；新增 MIN_CHUNK_SIZE = 60。

3. rag/__init__.py
   - 导出 split_document，移除 split_by_paragraph。

4. test/test_text_splitter.py（重写，13 个用例）
   - 核心断言是"切点不能落在句子中间"：每块必须以句末标点收尾、
     不得在英文单词中间断开、拼接回去要与原文完全一致。

5. test/retrieval_dataset.py + test/evaluate_retrieval.py
   - expected 改成能落在同一个合理片段里的核心证据词（原写法要求
     4 个关键词同时出现在 top3，任何 top_k 都无法满足）。
   - 评估输出增加"缺哪个关键词 / 哪条误召回"的明细。

--------------------------------------------------------------------------------
二、能实现什么（用户可感知的变化）
--------------------------------------------------------------------------------

1. 检索片段更"完整"：一段话不会被劈成两半，模型拿到的证据是通顺的原文。
2. 标题不再单独成块：chunk 开头就是有信息量的正文，向量质量提高。
3. 重叠更自然：重叠以整句为单位，不会出现"半句话重复"的碎片。
4. 英文文档不再被切坏单词（旧实现按字符切，会把 endpoint 切成 endpo/int）。
5. 超长无标点文本（日志、ID 串）仍然可控：单块不超过 max_chars。

实测数据（示例知识库 36 篇文档）：
  片段数 103 → 70；平均 95 字；最长 197 字；超过 300 字的 0 条。
  检索命中率 100%（5/5）；误召回 1/3（"公司股票代码"，已知案例）。
  真实模型 "公司在哪里？" → 检索命中 demo_company_overview.txt，
  SSE 86 个 delta + done，回答"深圳市南山区科技园"。

--------------------------------------------------------------------------------
三、兼容性 / 注意事项
--------------------------------------------------------------------------------

1. split_by_paragraph 已删除；如果别处引用它，改用 split_document。
   `from rag.splitter import split_text` 仍然可用，行为未变。
2. 分块结果变了 → 已建好的索引必须重建。程序内索引在 retrieve 首次调用时
   按知识库目录 mtime 自动重建；如果是外部向量库，需要手动重跑入库。
3. 参数含义：
   - max_chars  单片段目标上限（默认 300）
   - overlap    重叠预算，按整句回退（默认 50）
   - min_chars  短块吸附阈值（默认 60，设 0 可关闭吸附）
4. 测试数量：42 → 48（新增 6 个分块用例）。

二、requirements.txt 编码修复（这才是"看不了"的真正原因）
--------------------------------------------------------------------------------

  现象：编辑器打开 requirements.txt 是乱码 / 空白 / 提示二进制文件。

  诊断过程（不猜，直接看字节）：
    head -c 32 requirements.txt | od -c
    →   #  \0      \0   8   h 303   _ 235   O ...
  每个 ASCII 字符后面跟一个 \0，是典型的 UTF-16LE 特征；
  "核" 字编码为 38 68（U+6838 的小端表示），"心" 为 C3 5F（U+5FC3）。
  结论：文件是 UTF-16LE（且无 BOM），文件本身内容完好，只是编码不对。

  修复：
    raw  = Path('requirements.txt').read_bytes()
    text = raw.decode('utf-16-le')
    Path('requirements.txt').write_bytes(text.encode('utf-8'))
  文件大小 1112 → 694 字节（UTF-16 每字符 2 字节，转 UTF-8 后中文 3 字节、
  ASCII 1 字节，所以体积反而变小）。

  为什么必须修：
  - pip 读 requirements.txt 时按 locale 解码，UTF-16 在多数环境下会导致
    "Invalid requirement" 或直接解析失败，装依赖会踩坑。
  - git diff / 编辑器 / CI 全部按 UTF-8 处理，非 UTF-8 文本在协作里是定时炸弹。

四、两个技术点，值得单独说

  1) 改标题不能打乱会话顺序
     models.py 里 ChatSession.updated_at 挂了 onupdate=_utcnow。这是 Core 层的钩子：

     而会话列表正是按 updated_at 倒序排的 —— 于是「改个名字」会让会话跳到最上面，
     用户会以为列表乱了。

     修法：在 values() 里写 updated_at=ChatSession.updated_at，
     SQL 变成 SET updated_at = chat_sessions.updated_at，等于原地不动。

     这件事是写测试时才发现的：我原本的注释声称"不会碰 updated_at"，但代码其实会。
     test_rename_does_not_reorder_list 就是钉死它的 —— 改名前后的列表顺序必须完全一致。

  2) 本该 422 的请求变成了 500
     加上第一个自定义校验器之后，test_rename_session 直接崩：
       TypeError: Object of type ValueError is not JSON serializable

     原因：Pydantic v2 的 exc.errors() 会把校验器抛的**原始异常对象**塞进 ctx.error，
     而 api/exceptions.py 又把 errors() 原样丢给 JSONResponse。内置约束
     （min_length 之类）的 ctx 里是数字，所以这个坑在项目里躺了很久，从没被踩到。

     修法：新增 _serializable_errors()，用 jsonable_encoder 配
     custom_encoder={BaseException: str}。不修的话，以后任何自定义校验失败
     都会变成 500，而且报错信息完全指不到真正原因。

一、先修一个会 400 的真 bug

   原来 store.history() 是 `ORDER BY id DESC LIMIT 40` —— 取最近 40 **行**。
   而 OpenAI 协议要求：任何 role="tool" 的消息，前面必须紧跟一条带 tool_calls
   的 assistant。一次工具调用会写**两行**（assistant + tool），
   于是窗口边界可能正好落在一行 tool 上，送出去的对话以孤立 tool 开头 → 400。

   实测（不同历史长度扫一遍）：
       41/43/45/47 行 → 正常
       42/44/46/48 行 → 全部报错
   一半概率触发，开发时几乎不可能复现。

   修法不是"少取一条"或"跳过 tool"，而是换最小单位：
       一轮 = 一条 user 消息 + 它之后直到下一条 user 之前的所有消息
   按轮切，assistant(tool_calls) 和它的 tool 结果天然在同一边。

二、现在能做到什么（三层记忆）

   长期记忆（user_memories 表）  跨会话：这个人是谁、要什么
   会话摘要（chat_sessions.summary）  会话级：这段对话早期聊到哪了
   最近原文（chat_messages）      精确：刚才具体说了什么

   拼装顺序：
       system prompt
        ├─ 长期记忆块（按相关度挑，≤320 token）
        ├─ 【早期对话摘要】（挤出去的轮次压成 300 字以内）
        └─ 最近 N 轮原文（≤12 轮 / ≤3000 token）

   全部折进**一条** system 消息：不同服务商对"多条 system"处理不一致，
   有的直接 400，折成一条最稳。

四、几个刻意的取舍

   1) 摘要攒够了才压
      摘要是一次额外模型调用。每轮都压，成本和延迟都翻倍。
      所以挤出去的内容累积到 800 token 才压一次。
      代价：攒够之前，那几轮内容模型看不到（原文仍在库里）。

   2) 长期记忆不做向量检索
      记忆条数是几十条量级，为几十条数据加载 embedding 模型冷启动要几百毫秒，
      收益远小于成本。用字面二元组重合度排序就够。几千条再换。

   3) 让模型自己决定记不记，而不是每轮自动抽取
      每轮多一次模型调用、抽取质量还不稳定。交给 remember 工具更省也更好控。

   4) 记忆失败一律降级，不抛异常
      摘要挂了用旧摘要，长期记忆读不到就跳过。记忆是增强项，
      不能因为它出问题让用户发不出消息。

--------------------------------------------------------------------------------
一、新增能力：现在能做到什么
--------------------------------------------------------------------------------

1. 循环是显式的，不是藏在两处重复代码里
   以前 run() 和 stream() 各写了一遍「调模型 → 有工具就调 → 回灌 → 再来一轮」。
   现在只有一个 `_cycle()` 异步生成器，两条入口都消费它：
     run()    吞掉增量，只取最终答案
     stream() 把增量、思考、动作、观测都吐成事件
   "要不要流式"只在调模型那一步分叉（`_one_turn`）。

2. 思考过程可见
   模型调工具前输出的那段自然语言就是 Thought。新增 SSE 事件 `thought`：
     event: thought  {"text": "我先查一下报销制度", "step": 1}
   页面上它会渲染成一个虚线框的「思考」旁注，和正式答案分开；
   历史回放时，带 tool_calls 的 assistant 消息也标成 thought 回放
   （store.messages_for_api 里把 role 改写成 thought）。
   模型不说就直接调工具时返回空串 —— 不伪造思考。

3. 循环能被刹住
   新增 LoopGuard：同一工具 + 同一参数
     第 1 次     正常执行
     第 2 次     在观测结果前贴一句「换一个思路」的提醒（不是插 system 消息）
     第 3 次     直接中断，termination=loop
   参数比较前先 json.dumps(sort_keys=True) 归一化，
   否则 {"a":1,"b":2} 和 {"b":2,"a":1} 会被当成两个不同动作，守卫形同虚设。

4. 终止原因统一收口
   done 事件的 payload 固定包含：
     termination: answer | max_steps | loop | error
     steps / tool_calls / thoughts   用量
     trace: 每步的思考、动作、观测、是否终止（仅流式）
   出错也走 done 收尾，客户端不用靠"连接断了"猜结果。

5. 观测结果压缩
   单条工具输出超过 1200 字截断（REACT_OBSERVATION_LIMIT），
   并在末尾标注原文长度。存库的也是压缩版 —— 否则历史里躺着一堆
   两三千字的检索原文，下次对话直接吃满窗口。

三、为什么这么做（而不是那样）
--------------------------------------------------------------------------------

1) 为什么不用论文原版的纯文本 ReAct（Action: search({...})）
   参数里多一个引号、嵌套一层花括号，正则就崩；工具名拼错要到运行时才发现。
   这里用 function calling 做动作（schema 校验 + 调用 id 配对），
   只把「思考」显式化 —— 拿论文的好处，不接它的脆弱。

2) 为什么先抽纯逻辑再写循环
   循环里最容易出 bug 的不是"调模型"，而是判断：什么时候算卡死、
   观测要不要截断、这一步到底有没有答案。这些抽出来就能几十毫秒跑 24 个用例；
   埋在 async 生成器里就只能靠真调模型验，慢且不可靠。

3) 为什么阈值最低是 2
   阈值 1 意味着"第二次相同调用就掐断"，可并行调用和正常重试都会产生
   连续相同动作，会误杀。第 2 次提醒、第 3 次才中断。

4) 为什么出错后还要发 done
   SSE 响应头早就发出去了，改不了状态码。如果只有 error 没有 done，
   前端只能靠"流结束"来猜，拿不到终止原因和 trace。
   统一成"done 永远是最后一个事件"，客户端只认一个终态。

5) 为什么提醒贴在观测内容前面，而不是加一条 system 消息
   不同服务商对"对话中途出现 system role"的支持不一致，
   有的直接 400。贴在 tool 内容开头是兼容性最好的做法。

     Recall@3    前 3 个**不同文档**里是否命中期望文档（按文档去重，
                 否则一篇切成 3 个片段能一个人占满前三名）
     MRR@10      第一个相关文档名次的倒数
     拒答准确率  负样本中返回空结果的比例
     误拒率      正样本中返回空结果的比例 —— 必须和拒答率一起看，
                 否则把阈值调到无限高就能刷出 100% 拒答

3. 检索器加了消融开关（rag/retriever.py）
   search(query, top_k=..., *, mode="hybrid", apply_gate=True)
     mode = dense / sparse / hybrid
     apply_gate = False 时关掉相似度门槛

   为什么开关放进生产代码而不是评测脚本自己实现一份：
   评估必须测**线上真正跑的那条路径**。脚本里另写一份检索，
   测出来的数字和线上没关系。

4. 加了阈值扫描 + 分层留出集验证
   --sweep：开发集调参 → 留出集验证，避免"同一份数据既调参又汇报"。
   按 difficulty 分层切分。第一版用 crc32 纯随机切，留出集只剩 4 条负样本，
   拒答率"100%"其实只是 4 条里蒙对 4 条 —— 分层切分后是 13/7。

三、实测结果
--------------------------------------------------------------------------------

  环境：36 篇文档 → 70 个片段；bge-small-zh-v1.5；top_k=3，pool=10，rrf_k=60
  评测集：103 条（83 可回答 / 20 不可回答）

  配置                 Recall@3    MRR@10    拒答准确    误拒率    误召数
  ------------------------------------------------------------------------
  仅向量 dense           96.4%     0.903      45.0%     0.0%     11/20
  仅关键词 BM25          95.2%     0.932      45.0%     0.0%     11/20
  混合 RRF（生产）        97.6%     0.950      45.0%     0.0%     11/20
  混合 · 关门槛          98.8%     0.955       0.0%     0.0%     20/20

  按难度拆 Recall@3：       easy    medium     hard
  仅向量 dense             100%     100%      62%
  仅关键词 BM25            100%      98%      62%
  混合 RRF（生产）          100%     100%      75%
  混合 · 关门槛            100%     100%      88%

  ★ 但百分比会骗人，配对比较才是真的：
     对比                     混合赢   混合输    打平    净差
     混合 vs 仅向量 dense          1       0      82      +1
     混合 vs 仅关键词 BM25          2       0      81      +2
     混合 vs 混合·关门槛            0       1      82      -1

     全部四种配置都命中：78/83
     全部都没命中：      1/83
     **真正能区分优劣的：4/83**

  读法：97.6% vs 96.4% 的差距就是那 1 条用例。83 条样本上 1 条 = 1.2pp，
  这个量级是噪音，不是效果。

--------------------------------------------------------------------------------
四、三个发现（第二个是假设被数据否掉的）
--------------------------------------------------------------------------------

1) 混合检索：**测不出显著差异**（不是我一开始以为的"+1.2pp 提升"）

   聚合百分比看：
     Recall@3  97.6%  vs 96.4%（dense）/ 95.2%（BM25）
     MRR@10    0.950   vs 0.903 / 0.932

   乍看像有提升。但 83 条正样本里 **1 条就是 1.2 个百分点**，
   所以必须做配对比较（逐条比，而不是比总分）：

     对比                     混合赢   混合输    打平    净差
     混合 vs 仅向量 dense          1       0      82      +1
     混合 vs 仅关键词 BM25          2       0      81      +2
     混合 vs 混合·关门槛            0       1      82      -1

     全部四种配置都命中：78/83
     全部都没命中：      1/83
     **真正能区分优劣的：4/83**

   结论：混合检索赢的那 1~2 条是全评测集仅有的几处差异，
   在这个样本量上没有任何统计意义。**不能声称"混合检索更好"。**

   为什么测不出来（三条，都是评测集自己的问题）：
     a. 语料太小：36 篇 / 70 个片段，top_k=3 的覆盖率天然就高，
        78/83 是"怎么检都中"。天花板效应，没有提升空间。
     b. 题目泄漏原词：我是看着文档写的问题，easy+medium 占了 75/83，
        两路检索都能命中，差异根本不会出现。
     c. hard 只有 8 条：6/8 vs 5/8 就是 1 条用例 = 12.5pp 的假精度。

   能确定的一件事：**门槛确实在起作用**（关掉它召回 +1 条，拒答归零），
   但门槛的取舍是零和交易，见第 3 点。

2) 假设被否：误召**不是**关键词兜底通道造成的
   我原本的判断是"dense 低于门槛、但 BM25 命中的片段"把误召放进来了，
   于是给 RetrievedChunk 加了 matched_by 诊断，专门统计这条通道。
   结果：11 条误召里 **0 条**走的是兜底通道。

   也就是说，这 11 条都是**自己就越过了 0.55 的向量门槛**：
     "公司有多少台服务器" ↔ demo_company_overview（讲公司规模、办公方式）
     "数据库连接池设多大" ↔ demo_database_mysql
     "部署到 Kubernetes" ↔ demo_deployment_config
   语义上确实相关，但文档里**没有答案**。

   结论：embedding 相似度衡量的是"主题相关"，不是"答案蕴含"。
   拿一个全局相似度阈值当"能不能回答"的判据，本身就用错了信号。
   这不是调参能解决的事。

3) 调阈值是零和交易，不是改进
   开发集（68 条）扫描结果：
     floor=0.35 → 召回 98.2% / 拒答 30.8%
     floor=0.45 → 召回 97.6% / 拒答 45.0%   ← 当前生产
     floor=0.50 → 召回 92.7% / 拒答 76.9%
     floor=0.55 → 召回 90.9% / 拒答 92.3%   ← 开发集最优

   留出集（35 条，调参时没见过）验证：
     当前生产参数  召回 100.0% / 拒答 71.4% / balanced 85.7%
     扫描最优参数  召回  78.6% / 拒答 100.0% / balanced 89.3%

   开发集上 +6.8pp 的优势，到留出集只剩 +3.6pp，还付出了召回 -21pp 的代价。
   典型的过拟合迹象。

   所以**不改默认阈值**。当前参数站在"宁可多给证据、由模型层兜住拒答"这一侧，
   这个选择有它的道理：检索多给点，模型还能判断；检索给空了，模型连判断的机会都没有。

--------------------------------------------------------------------------------
五、验证
--------------------------------------------------------------------------------

   pytest -q  → 192 passed（187 → 192，新增 5 条消融开关测试）

   其中一条测试直接抓出了真 bug：dense 模式下结果仍被标成 matched_by="both"
   —— 因为 BM25 的排名表照样算了，标签没跟着 mode 走。
   这个 bug 不影响生产（生产就是 hybrid），但会让消融评测分不清
   "这条是向量找出来的还是关键词找出来的"，测出来的数字是假的。
   已修：只有参与排序的那一路才算命中，另一路的 rank 字段返回 None。

--------------------------------------------------------------------------------
六、结论与不做什么
--------------------------------------------------------------------------------

   做到的：
     - 有了 103 条标注集和可复现的消融脚本，指标定义写死在代码里
     - 证明了**当前评测集测不出三种检索方式的差异**（78/83 全命中，
       只有 4 条能区分），这本身是个有效结论 —— 它说明要继续做对比，
       问题在评测集的区分度，不在检索实现
     - 拒答短板定位到了根因（信号用错，不是参数没调好）

   没做到的：
     - "混合检索更好"这个结论**目前没有证据**，不能写进任何地方
     - 拒答能力仍是短板：20 条负样本里 11 条给了证据

   明确不做：
     - 不再调 threshold / floor（零和交易，留出集验证过会过拟合）
     - 不再从这份评测集里挤小数点位（1 条 = 1.2pp，挤出来是自欺）
