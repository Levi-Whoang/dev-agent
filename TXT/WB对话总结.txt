一、这次要做什么

在 dev-agent 的 WB 分支上一次性完成七件事（用户说明无先后顺序）：
  1. 构建一个简单的前端页面
  2. 数据库操作改成 SQLAlchemy，新增用户登录注册
  3. 新增 JWT 令牌
  4. 使用流式输出
  5. 优化代码结构，不同功能分文件
  6. 整体代码改成异步
  7. 优化 RAG，采用混合检索

附加要求：对话总结写进 TXT/WB对话总结.txt，改动说明写进 TXT/WB代码修改.txt，
两个文件都放 TXT 目录，以后每次改代码都要同步更新，并记录到分。

二、先读仓库，摸清现状

分支上被跟踪的文件只有 34 个，核心是：
  - app.py            6 个路由 + 3 个异常处理器全挤在一起，全同步
  - agent/agent.py    硬编码 system prompt，同步 OpenAI 客户端，10 轮决策循环
  - agent/session.py  裸 pymysql，手写 SQL，整段 messages 存一个 JSON 字段
  - tools/knowledge.py 只有向量检索（sentence-transformers + 余弦相似度）
  - 无前端、无鉴权、无流式、无 JWT

三、关键判断（以及为什么这么选）

1) 数据库默认 SQLite，而不是继续绑 MySQL
   本地 .env 里配了 MYSQL_HOST，但既没有 MySQL 服务也没装异步驱动 aiomysql，
   照原样改成 SQLAlchemy 异步会直接启动失败。
   决定：默认用 SQLite（aiosqlite），MySQL 作为可选项；
   若检测到 MYSQL_HOST 但缺 aiomysql，打印警告并降级到 SQLite，不让程序起不来。

2) 密码哈希用标准库 pbkdf2_hmac，不引 bcrypt / passlib
   少一个依赖、少一类版本坑，迭代 26 万次 + 每用户独立盐值足够。
   passlib 与新版 bcrypt 的兼容告警是有名的坑，教学项目没必要踩。

3) 消息表拆成行，而不是继续存整段 JSON
   原来 save() 覆盖整段 messages，两个人同时写同一会话会互相丢消息；
   现在一条消息一行，追加即 INSERT，顺带能用外键把会话绑到用户身上。

4) 流式用 SSE + fetch(ReadableStream)，不用 EventSource
   EventSource 只能发 GET、带不了 Authorization 头，而接口要 POST + JWT。

5) 请求日志中间件改为纯 ASGI，不用 @app.middleware("http")
   BaseHTTPMiddleware 包了一层流，遇到 StreamingResponse 容易把 SSE 的
   分块攒成一整块。纯 ASGI 只包一层 send，body 一个字节不碰。

6) 中文 BM25 用「连续汉字切二元组」，不引 jieba
   "深圳市南山区" → 深圳市/圳市南/市南山/南山区，不需要词典，召回够用，
   这也是 Elasticsearch cjk 分析器的思路。

7) 融合用 RRF，不做分数加权
   余弦 0~1、BM25 可以到 30+，直接相加等于让 BM25 独裁；
   RRF 只用名次（score = Σ 1/(k+rank)），天然免疫量纲差异。

四、实测数据（不是拍脑袋定的阈值）

用 scripts/generate_knowladge_base.py 生成 36 篇示例文档、6769 字、切出若干片段，
实测（bge-small-zh-v1.5，本机缓存）：

  查询                              稀疏 余弦   结果
  Python 类型标注是什么？            0.907  命中 3 条，全部来自 demo_python_types.txt
  这个实习岗位需要掌握哪些技术？      0.682  命中 3 条，含 Python/FastAPI 相关段落
  公司在哪里？                       0.600  命中深圳市南山区那条
  今天股市怎么样？                   0.411  BM25 为 0 → 判为无证据，返回空（符合预期）

结论：dense_threshold=0.55、dense_floor=0.45 这组参数在示例语料上

五、踩到的坑（都是实测发现的）

1) `from __future__ import annotations` 让工具注解变成字符串，
   动态建 Pydantic 模型后 model_json_schema() 报
   `calculateArgs is not fully defined`。
   修法：tools/schema.py 改用 typing.get_type_hints() 解析注解。

2) 同一个文件并行发两个 Edit 会互相覆盖（我先把 store.py 的一行改坏过一次，
   又漏掉了 maybe_autotitle 方法）。之后改成一次只改一个文件的一处。

3) FastAPI 0.143 的 include_router 是懒加载的（路由列表里只看到
   _IncludedRouter），一开始误以为路由没注册成功，其实启动后才展开。

4) 流式响应头已经发出后再抛异常，客户端只会看到「200 但空流」。
   修法：event_source 内部 try/except，把异常转成 error + done 事件发出去。

六、验证结果

  - pytest test/ -q → 42 passed
  - 真机启动 uvicorn，注册 → 登录 → /auth/me → /chat/stream 全链路通过：
    真实模型（deepseek-flash）调用了 knowledge_search_context，
    检索命中 demo_company_overview.txt，回答"深圳市南山区科技园"，
    SSE 共 61 个 delta 事件 + 1 个 done 事件。
  - 非流式 /chat 正常；无答案问题（公司股票代码）模型按证据拒答。
  - 静态页 / 返回 200，style.css、app.js 均 200。

七、留给用户处理的两件事

【2026-10-25 01:31】第 2 轮 · 分块策略从「一刀切」改成三级递归
--------------------------------------------------------------------------------

一、问题

用户反馈：向量切分太单一。
回看 rag/splitter.py 的 split_by_paragraph：按空行切段，段落超长就直接
split_text 定长硬切 300 字。后果是：
  - 切点落在句子中间，"团队规模约五十人，采用远程与现场" 和 "结合的办公方式"
    被劈成两个片段，两边都不完整，向量也变糊；
  - 短段落（标题）单独成块，"公司介绍（虚构示例）" 这种块几乎没有信息量，
    既召回不了又干扰排序。

二、改成什么

三级递归，优先级从粗到细：
  段落（空行）→ 句子（。！？；!?）→ 分句（，、：）→ 词/字（英文按单词）

三条配套规则：
  1. 短块吸附：< 60 字的段落并入相邻段，标题不再独立成块；
  2. 整句重叠：overlap=50 是预算，回退时按整句取，不会切半句；
  3. 只有句子切不开才降到词/字，英文单词始终保持完整。

三、为什么不给中文做真正的分词

jieba 那类词典包几十 MB，而切点落在词中间时重叠窗口已经把上下文补回来了，
收益远小于成本。所以最后一级是「英文按词、中文按字」的 token 流 + 定长窗口。
这一点在代码注释里写清楚了，避免以后有人以为"词级切分"没实现是漏了。

四、测试逼出来的三个真 bug（先写测试再改代码的价值）

1. 单个 token 超过上限（一长串没有空格和标点的 ID）会直接撑爆 chunk
   → 在 _split_tokens 里加了"单 token 超长就硬切"的分支。
2. 空白没进 token 流，拼回去变成 "timeoutwhilecallingendpoint"
   → 正则补上 \s+ 分支。
3. 原本想按内容全局去重，结果"字字字..."这类重复内容被去成 1 块
   → 去掉去重（重复的表格行、固定条款都是有效内容）。

五、实测（改完不是看代码，是看数字）

  - 片段数 103 → 70；平均 95 字，最长 197 字，超过 300 的一条都没有
  - demo_recruitment_backend.txt 被切成 2 块：标题 + 正文 130 字，
    加分项 96 字，都在句末收尾
  - 检索命中率 100%（5/5），误召回 1/3（"公司股票代码" 这个已知案例）
  - 真实模型端到端：问"公司在哪里？"→ 1 次工具调用、86 个 delta，
    回答"深圳市南山区科技园"，并注明来源 demo_company_overview.txt

六、顺手修的一件事

test/retrieval_dataset.py 的 expected 太严：一条问题要求
["Python","FastAPI","RAG","LLM API"] 四个词同时出现在 top3 里，
而这四个词分散在三篇文档四个片段中，任何 top_k 都不可能覆盖——
那测的不是检索质量，是数据集写错了。
改成"能落在同一个合理片段里的核心证据词"，评估输出也加了缺失词明细。

【2026-10-25 19:10】第 5 轮 · 清理残留目录 + 修复 requirements 乱码
--------------------------------------------------------------------------------

一、这轮的两个问题

  1. 上一轮说"删"之后命令被打断，app/ modules/ frontend/ 三个目录还躺在仓库里。
  2. "requirements看不了" —— 编辑器打开是乱码。

二、requirements.txt 为什么看不了

  我没有先假设"是不是编码坏了"，而是直接 od -c 看前 32 个字节：

      #  \0      \0   8   h 303   _ 235   O ...

  每个字符后面跟一个 \0 —— 这是 UTF-16LE 的指纹。
  "核" 是 38 68，"心" 是 C3 5F，都对得上 U+6838 / U+5FC3 的小端字节序。

  所以结论很干脆：文件内容一个字都没丢，只是存成了 UTF-16LE 且没有 BOM。
  没有 BOM 是最坑的地方 —— 编辑器连"这是 UTF-16"都猜不出来，
  只能当二进制或者按 UTF-8 硬解，于是满屏乱码。

  这也顺带解释了另一个隐患：pip 解析 requirements.txt 时是按 locale 解码的，
  UTF-16 在中文 Windows 上大概率解析失败，装依赖会报 Invalid requirement。
  也就是说这个文件不只是"看起来坏了"，它是真的会在安装环节炸。

  修法就是不猜、直接转：read_bytes → decode('utf-16-le') → encode('utf-8')。
  1112 字节变 694 字节（UTF-16 定长 2 字节/字符，UTF-8 下 ASCII 只占 1 字节）。

三、删目录之前先做的三件事

  hewier 说过"删"，但我没有直接 rm -rf 了事，先查了三样：

  1. git ls-files app modules frontend → 空。
     说明这三个目录里的文件从未进过版本库，删掉不会丢任何被跟踪的内容。
  2. find 看里面到底剩什么 → 只有 .pyc、一个旧 app.log、node_modules、dist。
     没有一行源码。源码在 v2.0 重构时就搬到 agent/ api/ auth/ database/
     rag/ web/ tools/ 下面了。
  3. 全项目 grep 引用 → 只有 test/conftest.py:42 的 `from app import app`。
     这行看着危险，其实是安全的：它导的是根目录的 app.py（组合根），
     不是 app/ 目录。删掉目录反而让这行不再有歧义。

  三件事都过了一遍才动手，删完 0 个残留，测试 48 全过。

四、一个值得记下来的经验

  "文件打不开"这类问题，第一反应不该是重写文件，而是看它到底是什么编码。
  一个 od -c 或者 read_bytes() 就能定性，比反复问"你用的什么编辑器"快得多。
  这次要是图省事直接重写一份 requirements.txt，内容虽然对，但版本号是
  从记忆里敲的，很可能跟本机实测版本对不上 —— 那才是真埋雷。

【2026-10-25 19:27】第 6 轮 · 重命名会话
--------------------------------------------------------------------------------

一、需求

   一句话："新增重命名会话"。

二、先定的几个取舍

   - 交互用「就地编辑」，不用 prompt()。
     prompt 是阻塞式模态框：不能改样式、移动端体验差，而且分不清
     "用户点了取消"和"用户清空了内容"。换成把 span 直接替换成 input，
     宽度不跳、上下文不丢。
   - 接口用 PATCH 而不是 PUT。
     PUT 的语义是整份替换，PATCH 是改局部字段。以后若要加"只改置顶标记"
     之类的字段，PATCH 还能继续加。
   - 越权返回 404 而不是 403。
     跟这个项目里其他会话接口保持一致，不给攻击者留"这个 id 真实存在"的探测口子。

三、过程中改了自己两次

  第一次（注释造假）：我先在 docstring 里写了"改标题故意不碰 updated_at，
  否则列表顺序会乱"，然后随手写 values(title=title)。写测试时才意识到
  models.py 给这列挂了 onupdate —— Core 的 update() 只要没显式赋值就会刷新它。
  也就是说我那段注释是假话，代码和注释正好相反。
  改成 values(title=title, updated_at=ChatSession.updated_at) 才成立。
  顺手在 docstring 里标了一句"这一行删掉，上面那段理由就作废"，免得以后
  有人"清理冗余代码"时把它删掉。

  第二次（真 bug）：测试跑出 422 变 500，TypeError: ValueError is not JSON
  serializable。这跟重命名功能本身没关系，是 api/exceptions.py 里躺了很久的
  隐患 —— 项目里之前一个自定义校验器都没有，所以从没被触发过。
  选择修处理器，而不是绕开它（比如改用一个内置约束来校验），
  因为绕开只是把坑留给下一个写校验器的人。

四、验证到哪一步，没做到的直说

  做到的：51 个测试全过；起真实服务用 HTTP 打完整个生命周期；
        静态资源确认没被新路由影响。
  没做到的：前端没在真浏览器里点过。agent-browser 的 daemon 起不来
        （open 挂住被 SIGTERM），内嵌的 playwright-core 也没装，
        为此下一整套 Chromium 不划算 —— 用户自己打开页面点两下更快。
        所以前端目前只过了 node --check 和逐行复核。

五、留给下次的

   - 前端没做双击重命名。想做的话有个坑：dblclick 之前会先发两次 click，
     而 click 会触发 selectSession → renderSessions → innerHTML 重建整张列表，
     于是 dblclick 拿到的 li / span 已经是脱离文档的孤儿节点，replaceWith 不生效。
     要么在 dblclick 处理里按 session_id 重新查一次 DOM，要么就只留按钮。
     这次选了后者：可靠 > 花哨。
