一、这次要做什么

在 dev-agent 的 WB 分支上一次性完成七件事（用户说明无先后顺序）：
  1. 构建一个简单的前端页面
  2. 数据库操作改成 SQLAlchemy，新增用户登录注册
  3. 新增 JWT 令牌
  4. 使用流式输出
  5. 优化代码结构，不同功能分文件
  6. 整体代码改成异步
  7. 优化 RAG，采用混合检索

附加要求：对话总结写进 TXT/WB对话总结.txt，改动说明写进 TXT/WB代码修改.txt，
两个文件都放 TXT 目录，以后每次改代码都要同步更新，并记录到分。

二、先读仓库，摸清现状

分支上被跟踪的文件只有 34 个，核心是：
  - app.py            6 个路由 + 3 个异常处理器全挤在一起，全同步
  - agent/agent.py    硬编码 system prompt，同步 OpenAI 客户端，10 轮决策循环
  - agent/session.py  裸 pymysql，手写 SQL，整段 messages 存一个 JSON 字段
  - tools/knowledge.py 只有向量检索（sentence-transformers + 余弦相似度）
  - 无前端、无鉴权、无流式、无 JWT

三、关键判断（以及为什么这么选）

1) 数据库默认 SQLite，而不是继续绑 MySQL
   本地 .env 里配了 MYSQL_HOST，但既没有 MySQL 服务也没装异步驱动 aiomysql，
   照原样改成 SQLAlchemy 异步会直接启动失败。
   决定：默认用 SQLite（aiosqlite），MySQL 作为可选项；
   若检测到 MYSQL_HOST 但缺 aiomysql，打印警告并降级到 SQLite，不让程序起不来。

2) 密码哈希用标准库 pbkdf2_hmac，不引 bcrypt / passlib
   少一个依赖、少一类版本坑，迭代 26 万次 + 每用户独立盐值足够。
   passlib 与新版 bcrypt 的兼容告警是有名的坑，教学项目没必要踩。

3) 消息表拆成行，而不是继续存整段 JSON
   原来 save() 覆盖整段 messages，两个人同时写同一会话会互相丢消息；
   现在一条消息一行，追加即 INSERT，顺带能用外键把会话绑到用户身上。

4) 流式用 SSE + fetch(ReadableStream)，不用 EventSource
   EventSource 只能发 GET、带不了 Authorization 头，而接口要 POST + JWT。

5) 请求日志中间件改为纯 ASGI，不用 @app.middleware("http")
   BaseHTTPMiddleware 包了一层流，遇到 StreamingResponse 容易把 SSE 的
   分块攒成一整块。纯 ASGI 只包一层 send，body 一个字节不碰。

6) 中文 BM25 用「连续汉字切二元组」，不引 jieba
   "深圳市南山区" → 深圳市/圳市南/市南山/南山区，不需要词典，召回够用，
   这也是 Elasticsearch cjk 分析器的思路。

7) 融合用 RRF，不做分数加权
   余弦 0~1、BM25 可以到 30+，直接相加等于让 BM25 独裁；
   RRF 只用名次（score = Σ 1/(k+rank)），天然免疫量纲差异。

四、实测数据（不是拍脑袋定的阈值）

用 scripts/generate_knowladge_base.py 生成 36 篇示例文档、6769 字、切出若干片段，
实测（bge-small-zh-v1.5，本机缓存）：

  这个实习岗位需要掌握哪些技术？      0.682  命中 3 条，含 Python/FastAPI 相关段落
  公司在哪里？                       0.600  命中深圳市南山区那条

五、踩到的坑（都是实测发现的）

2) 同一个文件并行发两个 Edit 会互相覆盖（我先把 store.py 的一行改坏过一次，
   又漏掉了 maybe_autotitle 方法）。之后改成一次只改一个文件的一处。

3) FastAPI 0.143 的 include_router 是懒加载的（路由列表里只看到
   _IncludedRouter），一开始误以为路由没注册成功，其实启动后才展开。

4) 流式响应头已经发出后再抛异常，客户端只会看到「200 但空流」。
   修法：event_source 内部 try/except，把异常转成 error + done 事件发出去。

【2026-10-25 01:31】第 2 轮 · 分块策略从「一刀切」改成三级递归
--------------------------------------------------------------------------------

一、问题

用户反馈：向量切分太单一。
回看 rag/splitter.py 的 split_by_paragraph：按空行切段，段落超长就直接
split_text 定长硬切 300 字。后果是：
  - 切点落在句子中间，"团队规模约五十人，采用远程与现场" 和 "结合的办公方式"
    被劈成两个片段，两边都不完整，向量也变糊；
  - 短段落（标题）单独成块，"公司介绍（虚构示例）" 这种块几乎没有信息量，
    既召回不了又干扰排序。

二、改成什么

三级递归，优先级从粗到细：
  段落（空行）→ 句子（。！？；!?）→ 分句（，、：）→ 词/字（英文按单词）

三条配套规则：
  1. 短块吸附：< 60 字的段落并入相邻段，标题不再独立成块；
  2. 整句重叠：overlap=50 是预算，回退时按整句取，不会切半句；
  3. 只有句子切不开才降到词/字，英文单词始终保持完整。

三、为什么不给中文做真正的分词

jieba 那类词典包几十 MB，而切点落在词中间时重叠窗口已经把上下文补回来了，
收益远小于成本。所以最后一级是「英文按词、中文按字」的 token 流 + 定长窗口。
这一点在代码注释里写清楚了，避免以后有人以为"词级切分"没实现是漏了。

四、测试逼出来的三个真 bug（先写测试再改代码的价值）

1. 单个 token 超过上限（一长串没有空格和标点的 ID）会直接撑爆 chunk
   → 在 _split_tokens 里加了"单 token 超长就硬切"的分支。
2. 空白没进 token 流，拼回去变成 "timeoutwhilecallingendpoint"
   → 正则补上 \s+ 分支。
3. 原本想按内容全局去重，结果"字字字..."这类重复内容被去成 1 块
   → 去掉去重（重复的表格行、固定条款都是有效内容）。

五、实测（改完不是看代码，是看数字）

  - 片段数 103 → 70；平均 95 字，最长 197 字，超过 300 的一条都没有
  - demo_recruitment_backend.txt 被切成 2 块：标题 + 正文 130 字，
    加分项 96 字，都在句末收尾
  - 检索命中率 100%（5/5），误召回 1/3（"公司股票代码" 这个已知案例）
  - 真实模型端到端：问"公司在哪里？"→ 1 次工具调用、86 个 delta，
    回答"深圳市南山区科技园"，并注明来源 demo_company_overview.txt

六、顺手修的一件事

test/retrieval_dataset.py 的 expected 太严：一条问题要求
["Python","FastAPI","RAG","LLM API"] 四个词同时出现在 top3 里，
而这四个词分散在三篇文档四个片段中，任何 top_k 都不可能覆盖——
那测的不是检索质量，是数据集写错了。
改成"能落在同一个合理片段里的核心证据词"，评估输出也加了缺失词明细。

【2026-10-25 19:10】第 5 轮 · 清理残留目录 + 修复 requirements 乱码
--------------------------------------------------------------------------------

一、这轮的两个问题

  1. 上一轮说"删"之后命令被打断，app/ modules/ frontend/ 三个目录还躺在仓库里。
  2. "requirements看不了" —— 编辑器打开是乱码。

二、requirements.txt 为什么看不了

  我没有先假设"是不是编码坏了"，而是直接 od -c 看前 32 个字节：

      #  \0      \0   8   h 303   _ 235   O ...

  每个字符后面跟一个 \0 —— 这是 UTF-16LE 的指纹。
  "核" 是 38 68，"心" 是 C3 5F，都对得上 U+6838 / U+5FC3 的小端字节序。

  所以结论很干脆：文件内容一个字都没丢，只是存成了 UTF-16LE 且没有 BOM。
  没有 BOM 是最坑的地方 —— 编辑器连"这是 UTF-16"都猜不出来，
  只能当二进制或者按 UTF-8 硬解，于是满屏乱码。

  这也顺带解释了另一个隐患：pip 解析 requirements.txt 时是按 locale 解码的，
  UTF-16 在中文 Windows 上大概率解析失败，装依赖会报 Invalid requirement。
  也就是说这个文件不只是"看起来坏了"，它是真的会在安装环节炸。

  修法就是不猜、直接转：read_bytes → decode('utf-16-le') → encode('utf-8')。
  1112 字节变 694 字节（UTF-16 定长 2 字节/字符，UTF-8 下 ASCII 只占 1 字节）。

三、删目录之前先做的三件事

  hewier 说过"删"，但我没有直接 rm -rf 了事，先查了三样：

  1. git ls-files app modules frontend → 空。
     说明这三个目录里的文件从未进过版本库，删掉不会丢任何被跟踪的内容。
  2. find 看里面到底剩什么 → 只有 .pyc、一个旧 app.log、node_modules、dist。
     没有一行源码。源码在 v2.0 重构时就搬到 agent/ api/ auth/ database/
     rag/ web/ tools/ 下面了。
  3. 全项目 grep 引用 → 只有 test/conftest.py:42 的 `from app import app`。
     这行看着危险，其实是安全的：它导的是根目录的 app.py（组合根），
     不是 app/ 目录。删掉目录反而让这行不再有歧义。

  三件事都过了一遍才动手，删完 0 个残留，测试 48 全过。

四、一个值得记下来的经验

  "文件打不开"这类问题，第一反应不该是重写文件，而是看它到底是什么编码。
  一个 od -c 或者 read_bytes() 就能定性，比反复问"你用的什么编辑器"快得多。
  这次要是图省事直接重写一份 requirements.txt，内容虽然对，但版本号是
  从记忆里敲的，很可能跟本机实测版本对不上 —— 那才是真埋雷。

【2026-10-25 19:27】第 6 轮 · 重命名会话
--------------------------------------------------------------------------------

一、需求

   一句话："新增重命名会话"。

二、先定的几个取舍

   - 交互用「就地编辑」，不用 prompt()。
     prompt 是阻塞式模态框：不能改样式、移动端体验差，而且分不清
     "用户点了取消"和"用户清空了内容"。换成把 span 直接替换成 input，
     宽度不跳、上下文不丢。
   - 接口用 PATCH 而不是 PUT。
     PUT 的语义是整份替换，PATCH 是改局部字段。以后若要加"只改置顶标记"
     之类的字段，PATCH 还能继续加。
   - 越权返回 404 而不是 403。
     跟这个项目里其他会话接口保持一致，不给攻击者留"这个 id 真实存在"的探测口子。

三、过程中改了自己两次

  第一次（注释造假）：我先在 docstring 里写了"改标题故意不碰 updated_at，
  否则列表顺序会乱"，然后随手写 values(title=title)。写测试时才意识到
  models.py 给这列挂了 onupdate —— Core 的 update() 只要没显式赋值就会刷新它。
  也就是说我那段注释是假话，代码和注释正好相反。
  改成 values(title=title, updated_at=ChatSession.updated_at) 才成立。
  顺手在 docstring 里标了一句"这一行删掉，上面那段理由就作废"，免得以后
  有人"清理冗余代码"时把它删掉。

  第二次（真 bug）：测试跑出 422 变 500，TypeError: ValueError is not JSON
  serializable。这跟重命名功能本身没关系，是 api/exceptions.py 里躺了很久的
  隐患 —— 项目里之前一个自定义校验器都没有，所以从没被触发过。
  选择修处理器，而不是绕开它（比如改用一个内置约束来校验），
  因为绕开只是把坑留给下一个写校验器的人。

四、验证到哪一步，没做到的直说

  做到的：51 个测试全过；起真实服务用 HTTP 打完整个生命周期；
        静态资源确认没被新路由影响。
  没做到的：前端没在真浏览器里点过。agent-browser 的 daemon 起不来
        （open 挂住被 SIGTERM），内嵌的 playwright-core 也没装，
        为此下一整套 Chromium 不划算 —— 用户自己打开页面点两下更快。
        所以前端目前只过了 node --check 和逐行复核。

五、留给下次的

   - 前端没做双击重命名。想做的话有个坑：dblclick 之前会先发两次 click，
     而 click 会触发 selectSession → renderSessions → innerHTML 重建整张列表，
     于是 dblclick 拿到的 li / span 已经是脱离文档的孤儿节点，replaceWith 不生效。
     要么在 dblclick 处理里按 session_id 重新查一次 DOM，要么就只留按钮。
     这次选了后者：可靠 > 花哨。

【2026-10-27 16:47】第 7 轮 · 完善 Agent 记忆
--------------------------------------------------------------------------------

一、需求

   一句话："完善 agent 的 memory 功能"。

   我先把现状读了一遍，没有直接动手：
   `store.history()` 取最近 40 行消息塞给模型 —— 这就是当时的全部"记忆"。
   读的过程中发现一个会直接报错的 bug，于是这轮的起点变成了"先修 bug"。

二、那个 bug 值得单独讲

   按"行"裁剪和按"轮"裁剪，看起来只是粒度差别，实际上是能不能跑起来的差别。

   OpenAI/DeepSeek 的协议里，role="tool" 的消息必须紧跟在带 tool_calls 的
   assistant 后面。而一次工具调用写两行。40 是偶数，历史行数又是变化的，
   于是窗口边界有可能正好切在一行 tool 上 → 对话开头是一条孤儿 tool → 400。

   我没有靠推理下结论，直接造了 41~48 行八种历史跑了一遍：
   奇数行全正常，偶数行全报错。一半概率。

   为什么这个 bug 之前没被发现：正常聊天一次工具调用才两行，
   要聊到 40 行以上才进入这个区域；而且触发与否取决于总行数的奇偶，
   开发时手动点几下根本碰不到。

   顺便说明我为什么敢直接删掉 history()：全项目只有 agent.py 一处在用。
   留着一个"看起来能用、实际上有一半概率崩"的方法，比删掉危险得多。

三、三层记忆的分工

   我犹豫过要不要做跨会话的长期记忆。最后做了，原因是：
   摘要解决的是"同一段对话里记不住前面"，而"我是后端开发，别看 Java 岗位"
   这种信息天生该跨会话 —— 开个新会话就忘，用户会觉得这个助手很蠢。

   两者的生命周期完全不同，所以分两张表：
     摘要   随对话推进不断重写，一个会话一份
     长期记忆 一条条累积，很少变，跟着用户走
   混在一起迟早要么被误删，要么检索时互相干扰。

四、几个我自己改过的地方

   1) 一开始 _refresh_summary 无条件调 store.get_session()，
      结果测试里的假 store 被迫实现一整套接口。
      改成"关掉摘要就先短路"——顺带让记忆层对 store 的依赖降到最低。

   2) remember 工具最初想写普通函数，发现 db/user_id 会出现在 schema 里，
      模型有可能自己编一个 user_id 传进来。改用闭包焊死上下文，
      模型只看到 content 和 kind。

   3) prepare() 忘了把 ORM 行转成 MemoryMessage，测试直接报
      'ChatMessage' object has no attribute 'tokens'。
      顺手把 window 做成不依赖 SQLAlchemy 的纯函数 —— 纯函数好测，
      90 种边界组合跑完只要 1.5 秒。

   4) chat_router 里 user.id 要在生成器外面先取出来。
      生成器执行时请求级 db 可能已关闭，再去碰 user 对象会 DetachedInstanceError。

五、验证方式：三层都往下压了一级

   逻辑层：158 个测试（新增 107）。最关键的是扫 90 种边界，断言工具配对永远完整。
   数据层：拿真实的 dev_agent.db 跑升级，看列有没有加上、7 个老会话有没有丢。
   模型层：真调 deepseek-flash 跑两个会话。
           会话A 里模型自己决定调用 remember（说明 schema 被真实 API 接受，
           这一步任何单元测试都替代不了），会话B 是新会话，
           system prompt 里带上了记忆，回答变成"后端开发实习岗位 — 最匹配"。
   测试数据全部清理，没留垃圾。

六、留给下次的

   - agent/session.py 是 v1 留下的 pymysql SessionManager，现在的代码完全不用它
     （v2 走 SQLAlchemy）。和 sessions.db / sessions.json 一样属于该清的遗留物。
   - 长期记忆上限 60 条，超了 remember 直接拒绝。没有做淘汰策略，
     也没做前端管理界面。
   - 摘要只在"挤出窗口"时触发。如果用户在超长对话中途直接关掉页面，
     还没被压缩的早期内容就只是留在库里、不参与后续对话。

--------------------------------------------------------------------------------
一、需求原话与理解
--------------------------------------------------------------------------------

   原话：「做一个完整的react循环」

   先确认了歧义点：这里要的是 AI 的 ReAct（Reasoning + Acting）模式，
   不是 React 前端框架 —— 项目前端本来就是原生 HTML/CSS/JS，没有构建链。
   用户要的是让 Agent 的"想一步、做一步、看结果、再想"变成显式且可观测的东西。

   现状问题：run() 和 stream() 各写了一遍决策循环，
   改一处必须记得改两处；而且一旦模型拿同一个参数反复重试失败的工具，
   只能等 max_iterations 耗尽，用户干等半分钟什么也拿不到。

--------------------------------------------------------------------------------
二、做法：三层拆开
--------------------------------------------------------------------------------

   1) 策略层 —— 新建 agent/react.py，纯函数、纯数据结构，不碰模型也不碰数据库
      ReactStep / ReactTrace  单步与整条轨迹（思考 / 动作 / 观测 / 是否终止）
      LoopGuard               重复动作守卫，三级：正常 → 提醒 → 中断
      normalize_arguments     参数归一化（sort_keys），否则换键顺序就绕过守卫
      compress_observation    观测截断到 1200 字
      extract_thought         从正文取思考；取不到就是空，不伪造

   2) 循环层 —— 重写 agent/agent.py
      只有一个 _cycle() 异步生成器，run() 和 stream() 都消费它。
      内层 _one_turn() 是"一次模型调用"：流式时边收边吐 delta，
      结束时把（完整文本, 工具调用）交回上层。
      这样"要不要流式"只在一个地方分叉，决策逻辑不存在第二份。

   3) 呈现层 —— thought 事件 + done 里的 trace
      新增 SSE 事件 thought；done 统一携带 termination 与用量。
      前端收到 thought 时把当前气泡就地冻结成虚线"思考"旁注，另起气泡接答案
      —— 不这么做的话，页面会出现"我要查一下…+ 正式答案"黏成一段的自言自语。

--------------------------------------------------------------------------------
三、几个关键判断
--------------------------------------------------------------------------------

   1) 不退回论文原版的纯文本 ReAct
      论文让模型输出 `Action: search({"q": "..."})` 再用正则解析。
      参数里一个引号、一层花括号就崩，工具名拼错要到运行时才发现。
      我们的做法：动作走 function calling（schema 校验 + id 配对），
      只把"思考"这一步显式化。拿论文的好处，不接它的脆弱。

   2) 循环必须能刹住，但别刹太早
      阈值设为 1 会把"并行调用"和"正常重试"误判成卡死。
      最终定成：第 2 次相同 → 贴提醒；第 3 次 → 中断。
      提醒不做成 system 消息，而是贴在 tool 内容开头 ——
      不同服务商对"对话中途出现 system role"的支持不一致，有的直接 400。

   3) 出错后也要发 done
      SSE 头已经发出去了，改不了状态码。如果只有 error 没有 done，
      客户端只能靠"流结束"来猜。统一约定：done 永远是最后一个事件。

   4) 思考不能伪造
      模型不说直接调工具时，extract_thought 返回空串，不生成
      "用户想了解一下…"这种话。伪造的推理会污染日志和 trace，
      比没有更糟。

--------------------------------------------------------------------------------
四、验证方式
--------------------------------------------------------------------------------

   逻辑层：187 个测试（158 → 187）。
     新增 test_react.py 24 条，全部纯逻辑，0.4 秒跑完；
     test_agent_stream.py 补 5 条行为测试：
       思考事件顺序 / 静默不伪造 / 重复中断只执行两次 / 提醒注入到观测 /
       步数用尽收尾。

   模型层：真调 deepseek-flash，真 SQLite，真知识库（logs/e2e_react.py）。
     提问："公司报销流程是什么？顺便算一下 1280 加 720 等于多少。"
     第一步：思考 + 两个动作并行（检索 + 计算）
     第二步：发现检索偏题，自己换关键词重试（"费用报销 发票 审批 财务制度"）
     第三步：给出 2000，报销部分明确拒答并说明两次检索都没依据
     结果：termination=answer，steps=3，tools=3

   这一跑把三件单元测试替代不了的事一次性证明了：
     - 模型确实会在正文里先写思考（thought 非空）
     - 一次响应里的多个 tool_calls 能在同一步并行跑
     - 第一次偏题后是换关键词重试，不是原样重调 —— 说明 LoopGuard 没误杀

--------------------------------------------------------------------------------
五、留给下次的
--------------------------------------------------------------------------------

   - 历史回放虽然把思考标成了 role=thought，但没显示当时调用了哪个工具。
   - LoopGuard 只盯"紧邻的上一个动作"，三步一循环的情况仍靠 max_iterations 兜底。

三、第一次结论是错的，被用户一句话问倒
--------------------------------------------------------------------------------

   我最初写的结论：
     "混合检索确实更好：Recall@3 从 96.4% 提到 97.6%，MRR 从 0.903 提到 0.950，
      收益主要在排序质量上。"

   用户原话：「这不是没提升多少吗」

   对。做配对比较之后：
     混合 vs 仅向量   赢 1 条 / 输 0 条 / 平 82 条
     混合 vs 仅 BM25  赢 2 条 / 输 0 条 / 平 81 条
     混合 vs 关门槛   赢 0 条 / 输 1 条 / 平 82 条
     四种配置全部命中 78/83，全部失败 1/83，**能区分优劣的只有 4/83**

   83 条正样本里 1 条 = 1.2 个百分点。96.4% → 97.6% 就是**一条用例**。
   把噪音写成提升，和《项目简历描述规范》里批判的"没有测试依据的准确率"
   是同一件事。

--------------------------------------------------------------------------------
四、为什么测不出差异（问题在评测集，不在检索）
--------------------------------------------------------------------------------

   1) 语料太小：36 篇 / 70 个片段，top_k=3 的覆盖率天然就高，
      78/83 是"怎么检都中" —— 天花板效应，没有提升空间。
   2) 题目泄漏原词：我看着文档写问题，easy + medium 占 75/83，
      两路检索都能命中，差异不会出现。
   3) hard 只有 8 条：6/8 与 5/8 的差别就是 1 条 = 12.5pp 的假精度。

   一句话：一个 94% 样本"谁来都答对"的评测集，没有能力区分任何方案。

--------------------------------------------------------------------------------
五、仍然成立的两条
--------------------------------------------------------------------------------

   1) 门槛确实在起作用
      关掉门槛：召回只多 1 条，拒答从 45% 直接归零（20/20 误召）。
      所以门槛留着是对的。

   2) 拒答 45% 的根因找到了，而且**不是**我一开始猜的那个
      我原以为误召是"关键词兜底通道"（dense 低于门槛但 BM25 命中）放进来的，
      加了 matched_by 诊断专门统计 → **0/11**。
      这 11 条都是自己就越过了 0.55 门槛：
        "公司有多少台服务器" ↔ 公司介绍（讲规模和办公方式）
        "数据库连接池设多大" ↔ MySQL 文档
      语义上相关，但文档里没有答案。

      结论：embedding 相似度衡量"主题相关"，不是"答案蕴含"。
      拿全局相似度阈值当"能否回答"的判据，信号就用错了 —— 不是调参能解决的。

   3) 调阈值是零和交易（顺带验证过）
      开发集上 floor 0.45→0.55：拒答 45%→92%，召回 97.6%→90.9%。
      拿到分层留出集（35 条）验证：拒答 71.4%→100%，召回 100%→78.6%。
      开发集的 +6.8pp 优势到留出集只剩 +3.6pp，代价是召回 -21pp —— 过拟合。
      **所以默认参数一个字没动。**
