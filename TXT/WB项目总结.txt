================================================================================
一、一句话定位
================================================================================

  一个带工具调用、三层记忆和混合检索的企业知识库问答 Agent。
  目标用户是"想问公司内部制度、但不想翻文档"的员工。

  它现在处于什么阶段：**功能闭环已通，工程证据不足。**
  —— 换句话说：能演示、能讲设计，但拿不出数据证明"我的方案更好"。


================================================================================
二、技术栈与规模
================================================================================

  后端    FastAPI + 异步 SQLAlchemy 2.0 + SQLite/MySQL + JWT
  模型    OpenAI 兼容接口（实测 deepseek-flash），function calling
  检索    sentence-transformers(bge-small-zh) + BM25 + RRF 融合
  前端    原生 HTML/CSS/JS 单页，SSE 流式（无构建链）
  测试    pytest + pytest-asyncio，187 条

  代码量（不含 .venv）

     agent/        1876 行    ReAct 循环 + 三层记忆 + 事件定义
     rag/           755 行    加载 / 三级切分 / BM25 / RRF 融合
     web/           952 行    单页前端（HTML/CSS/JS）
     api/           520 行    路由 + 中间件 + 异常处理
     auth/          307 行    PBKDF2 + JWT
     database/      284 行    4 张表
     tools/         253 行    工具注册 + schema 生成
     入口与配置     397 行    app / config / logging / main
     ------------------------------------------------
     合计          ~5340 行    另加测试 2100 行

  知识库：36 篇 demo 文档，47 KB（演示规模，不是生产规模）


================================================================================
三、实际做到了什么
================================================================================

--------------------------------------------------------------------------------
3.1 ReAct 循环（agent/agent.py + agent/react.py）
--------------------------------------------------------------------------------

  做到了：
  - 一个 `_cycle()` 异步生成器，run() 和 stream() 共用，
    "要不要流式"只在调模型那一步分叉（v2.0 是两份实现，已消除）
  - Thought → Action → Observation 显式推进，Thought 以 SSE 事件暴露
  - 循环守卫 LoopGuard：同一工具 + 同一参数，第 2 次贴提醒、第 3 次中断
  - 四种终止原因（answer / max_steps / loop / error），done 永远是最后一个事件
  - 工具结果超 1200 字截断后才回灌
  - 判断逻辑抽成纯函数，24 条用例 0.4 秒跑完

  验证过：真模型跑"查报销 + 算加法"，3 步完成，模型自己换关键词重试一次。

  没验证过：**多用户并发下这套循环的表现。**

--------------------------------------------------------------------------------
3.2 三层记忆（agent/memory/）
--------------------------------------------------------------------------------

  做到了：
  - 长期记忆：user_memories 表 + `remember` 工具，跨会话注入 system prompt
  - 会话摘要：超出窗口的早期对话压成一段话，带 summary_upto_id 增量压缩
  - 最近窗口：按"轮"切而不是按"条"切，保证 tool 消息和它的 tool_calls 不被拆开
  - token 估算不引 tiktoken（中文按 1 字 1 token 保守估算）
  - 记忆层任何故障都降级，不阻断主流程

  验证过：跨会话实测（会话A 说身份 → 会话B 新会话回答个性化）；
          90 种边界组合断言工具配对永远完整。

  没验证过：记忆条数上限（60）在长期使用后的表现，没有淘汰策略。

--------------------------------------------------------------------------------
3.3 混合检索（rag/）
--------------------------------------------------------------------------------

  做到了：
  - 三级递归切分：段落 → 句子 → 分句/词，短块吸附，整句重叠
  - 稠密（向量）+ 稀疏（BM25，中英混合分词）双路召回，RRF 融合
  - 双层门槛：dense_threshold 判定"算不算有证据"，dense_floor 拦纯关键词命中
  - 证据不足返回 NO_RELEVANT_EVIDENCE，靠协议而不是靠提示词约束模型

  没做到：没有 reranker，没有向量持久化（每次启动重算），没有增量索引，
          知识库改了要重启进程。

--------------------------------------------------------------------------------
3.4 工程骨架
--------------------------------------------------------------------------------

  做到了：
  - 全异步：异步路由 + 异步 DB + 异步 LLM 客户端；同步工具进线程池
  - JWT 鉴权 + PBKDF2（26 万次迭代，只用标准库）+ 会话按用户隔离
  - SSE 流式：自定义事件协议，思考/动作/观测/终止全程可见
  - 统一响应体 {code, message, data} + 全局异常处理器
  - 配置集中在 config.py，测试只改一个点就能换数据库
  - 187 条测试，含 API 层的端到端（httpx）

  没做到：没有 CI，没有 Dockerfile，没有限流，没有指标/追踪，
          没有灰度或回滚方案。

四、当前的真实水平（自评，不打分只列事实）
================================================================================

  ✅ 设计上有明确取舍，且能说清为什么
     - 为什么用 function calling 做动作而不是文本解析 ReAct
     - 为什么按"轮"切历史而不是按"条"
     - 为什么记忆失败要降级而不是抛异常
     这些在 TXT/WB代码修改.txt 里都有"为什么这么做（而不是那样）"的段落。

  ✅ 踩过的坑是真实的、可复述的
     - 按条数截断历史导致 tool 配对断裂 → 400（用 41/43/45 对 42/44/46 的对照实验定位）
     - create_all() 不给已有表加列 → 手写幂等 ALTER
     - Pydantic v2 的 ValidationError 里嵌了原始异常 → JSONResponse 序列化 500
     - SSE 头已发出后无法改状态码 → 统一用 done 收尾
     - 加消融开关后 dense 模式仍被标 matched_by="both"（测试抓到的，已修）

  ✅ 检索侧已有量化数据【2026-10-28 补】
     103 条标注集上的四组消融，混合检索的收益第一次有数字。
     更重要的是：拒答只有 45% 这件事被定位到了根因（信号用错，不是参数没调好），
     并且试过调参 —— 留出集验证证明调参是零和交易，所以没改默认值。

  ⚠️ 缺"性能数据"
     检索质量有了，但耗时、QPS、成本一个都没有。
     这是现在最硬的一条。

  ⚠️ 只跑过单进程、单用户、本机
     没有并发压测，不知道 QPS、P95 延迟、embedding 会不会阻塞事件循环。

  ⚠️ 知识库是 36 篇 demo 文档
     演示够用，但撑不起"处理过真实企业文档"的说法。
     103 条评测集的结论也受这个规模限制，不能外推。

5.1 硬伤（不补，面试一问就露）
--------------------------------------------------------------------------------

  1) ✅ 量化评测【2026-10-28 已补，但结论是"测不出差异"】
     现状：test/retrieval_eval_set.py（103 条）+ test/evaluate_retrieval.py
          （四组消融 + 配对比较 + 阈值扫描 + 分层留出集验证）。

     实测（36 篇 → 70 片段，bge-small-zh，top_k=3）

       配置               Recall@3   MRR@10   拒答准确   误拒率
       --------------------------------------------------------
       仅向量 dense         96.4%    0.903     45.0%    0.0%
       仅关键词 BM25        95.2%    0.932     45.0%    0.0%
       混合 RRF（生产）      97.6%    0.950     45.0%    0.0%
       混合 · 关门槛        98.8%    0.955      0.0%    0.0%

     但这组百分比不能直接用。配对比较（逐条比）后：
       混合 vs 仅向量：赢 1 条 / 输 0 条 / 平 82 条
       四种配置全部命中 78/83，全部失败 1/83，**能区分优劣的只有 4/83**

     结论：**"混合检索更好"目前没有证据。** 1 条用例 = 1.2pp，
          这个量级是噪音。评测集顶到天花板了（78/83 怎么检都中），
          不是检索实现的问题，是评测集的区分度不够。

     能说出来的话（诚实版）：
       - "我搭了 103 条标注集的消融框架，用配对比较发现现有语料下
          三种检索方式在 79/83 条上没有差异 —— 说明我的评测集区分度不足，
          要先扩语料、加干扰文档，才谈得上比较。"
       - "混合检索相比单路只多命中 1~2 条，不足以支撑结论，我没有把它写成提升。"

     还没解决的：
       - 拒答准确率只有 45%，20 条负样本里 11 条给了证据。
         诊断证明**不是**关键词兜底通道造成的，而是这 11 条自己就越过了
         0.55 的向量门槛 —— embedding 衡量的是"主题相关"，不是"答案蕴含"。
       - 调阈值是零和交易：留出集上把拒答从 71% 拉到 100%，
         代价是召回从 100% 掉到 78.6%。所以没改默认参数。

     ⚠️ 简历上**不能**写"检索准确率提升"。
        能写的是："搭建 103 条标注集的检索评测框架（含 20 条强干扰负样本），
        用配对比较验证三种召回策略的差异，并据此判断现有语料区分度不足"——
        写方法，不写没发生的提升。

  2) 没有并发与性能数据
     现状：只在单进程单用户跑过。
     问题：senior 面试官问的第一个问题往往是"QPS 多少、瓶颈在哪"。
          现在答不出来；更糟的是 embedding 是 CPU 计算，
          并发时会和事件循环抢线程，理论上会拖慢整个服务。
     补法：locust/k6 打 50~100 并发，记录 P50/P95、错误率、CPU；
          把 embedding 改成批量 + 独立队列，再测一次对比。
     价值：这才是"企业级"和"能跑的 demo"的分界线。

  3) 没有可观测性
     现状：只有 logging，一次提问的 5 次模型调用在日志里是散落的。
     问题：出现"回答慢/答错"时无法定位到底是检索慢、模型慢还是守卫拦了。
     补法：给每次请求一个 trace_id，记录每步的耗时和 token 用量，
          最后汇总成一条结构化日志（JSON）。不需要上 OpenTelemetry。
     价值：面试时可以讲"我怎么定位到一个 P95 毛刺是检索引起的"。

--------------------------------------------------------------------------------
5.2 加分项（有则明显加分）
--------------------------------------------------------------------------------

  4) 容器化 + 一条命令跑起来
     现状：没有 Dockerfile。别人 clone 下来要装 torch（2G+）、下模型、配 .env。
     补法：多阶段构建 + 模型预热到镜像里，`docker compose up` 即可访问。
     价值：这是"工程完整度"最直观的信号，成本却很低（半天）。

  5) 成本与预算控制
     现状：一次提问最坏 10 轮 × (检索 + 模型)，没有任何预算上限或计量。
     补法：累计本次对话的 token 用量，超过阈值降级（少检索、缩短上下文）；
          记录每次请求的成本，出一个"每日花费"统计。
     价值：企业场景必问"这一问多少钱"，答不上来显得没落地过。

  6) 健壮性
     现状：模型超时/限流/返回畸形 JSON 的重试与降级没专门测过。
     补法：给 LLM 客户端加重试（指数退避 + 只重试可重试的错误码），
          用假客户端模拟 429 / 超时 / 空 choices，断言行为。

  7) 安全面
     现状：有限流缺失、无 prompt 注入防护、JWT 无刷新与吊销。
     补法（按性价比）：登录限流 → 知识库内容渲染时与指令分隔（防注入）
          → refresh token。
     价值：讲清楚"我知道知识库内容可能被当成指令"这一点，
          比真的做全了更能体现判断力。

--------------------------------------------------------------------------------
5.3 锦上添花（有余力再做）

  8) reranker（bge-reranker）→ 能讲"两阶段召回"的取舍
  9) 向量持久化 + 增量索引 → 能讲"文档更新怎么办"

六、最短补齐路径（按投入产出排序）
================================================================================

  第 1 步 ⚠️ 部分完成（2026-10-28）：评测框架建好了，但区分度不够
     → 103 条标注集、四组消融、配对比较、留出集验证都已经能跑
     → 但 78/83 全命中，只有 4 条能区分三种方案 —— 结论立不起来
     → 这一步的价值是"发现了评测集自己的问题"，不是拿到了提升数字

  第 1.1 步（下次优先，1 天）：先修评测集的区分度
     → 扩语料到 150~300 篇，其中放干扰文档（同主题、不同细节，
       关键词命中但语义指向错误）
     → 问题全部改写成口语短句，基本取消 easy 档
     → 验收：能区分优劣的样本 ≥ 40/100。达不到，任何方案比较都是自欺

  第 1.5 步（1 天）：换判断信号，别调旋钮
     → 假设：cross-encoder 重排（bge-reranker）能区分"主题相关"和"答案蕴含"
     → 前提是第 1.1 步做完，否则召回顶在天花板，看不出重排收益

  第 2 步（1 天）：加 trace_id + 每步耗时/token 统计
     → 结构化日志一条能看完整链路
     → 顺带就有了"平均几轮工具调用、平均耗时"这些能写进简历的数字

  第 3 步（1 天）：并发压测
     → 50 并发，出 P50/P95/错误率；找出瓶颈（大概率是 embedding）
     → 改批量推理，再测一次，形成"发现问题 → 优化 → 复测"的完整故事

  第 4 步（半天）：Dockerfile + compose
     → 让"能跑"这件事对别人成立

  完成 1 / 2 / 3 三步，这个项目就从"功能闭环"变成"有证据的工程"。
  再往上（reranker、增量索引、配额）属于加分，不着急。

七、面试会怎么问，现在能答到什么程度
================================================================================

  按"能不能答上"分类，比打分诚实：

  现在就能答的（设计类）
     - 为什么用 ReAct 而不是一次性回答？
     - 怎么防止模型无限循环？            （LoopGuard 三级拦截，讲得清）
     - 历史太长怎么办？                  （三层记忆 + 按轮切）
     - 为什么不用 LangChain？             （手写更可控，这个理由成立）
     - 工具参数传错了会怎样？             （Pydantic 校验后返回 error，让模型自己改）
     - 混合检索比单路好多少？            （框架有了，但**测不出差异** ——
                                          78/83 全命中，只有 4 条能区分，
                                          这个诚实回答比编个数字强）

  现在能答出"过程"的（比有数字更值钱）
     - 你的系统为什么拒答不准？
       → 查过了：不是关键词兜底通道（0/11），是 embedding 相似度衡量的是
         "主题相关"而非"答案蕴含"；调阈值是零和交易，留出集验证过会过拟合。
         下一步该换信号（cross-encoder 重排），不该继续拧旋钮。
     - 你怎么证明你的检索方案更好？
       → "我没证明。搭了框架，配对比较发现 83 条里只有 4 条能区分三种方案，
         说明我的评测集区分度不够。先扩语料加干扰文档，再谈优势。"
         这个回答比硬凑一个百分比可信得多，也是面试官真正想听的。

  半答的
     - 线上回答变慢了怎么查？            → 只有日志，没有 trace，只能靠猜
     - 知识库更新了怎么办？              → 答案成立但是"要重启进程"，不漂亮

  现在答不上的（数据类）
     - QPS 多少？瓶颈在哪？              → 缺压测
     - 一次提问多少钱？                  → 缺 token 计量
     - 端到端拒答率是多少？              → 只测了检索层，模型层没测（要花钱）
     - 怎么防知识库里的注入内容？        → 没做，也还没想过

  结论：**设计类问题基本能答；检索类的数据有了，性能/成本类的还缺。**
  下一步最该做的是压测和 trace —— 它们同时也是补数据的手段。


================================================================================
八、一句话结论
================================================================================

  这个项目的技术水平已经够写进简历了，但现在的写法只能写
  "我实现了一个基于 ReAct 的企业知识库问答 Agent"，
  写不成"我把检索召回率从 X 提到 Y、把 P95 从 A 降到 B"。

  【2026-10-28 更新】评测做了，但**没有拿到可用的提升数字**：
     - 混合检索 vs 单路：83 条里赢 1~2 条、平 82 条。
       78/83 是"怎么检都中"，只有 4 条能区分。这是噪音，不是提升。
     - 原因在评测集自己：语料只有 36 篇、题目贴着文档写、easy+medium 占 75/83。
       天花板效应 —— 没有提升空间，测什么都一样。
     - 所以这一步真正的产出是"知道该怎么修评测"，不是一个百分比。

  后半句（性能类）还缺：P95、QPS、单次成本。补法见第六节第 2~3 步。

  差的不是功能，是**证据**。检索侧的评测框架有了，但结论还没立起来；
  性能类的证据一条都没有。
