二、当前项目能完成哪些任务
这是一个 Python/FastAPI 的知识库问答 Agent 原型，能够把 Web API、模型工具调用、检索、会话数据库串成一条流程：

1. 通过 POST /chat 接收问题，调用 OpenAI 兼容聊天接口。Agent 允许模型决定是否调用已注册工具；最多循环 10 轮，并把工具结果送回模型生成最终回复。
2. 根据工具函数签名生成 JSON Schema，收到模型调用后用 Pydantic 再校验参数；代码区分了 JSON 解析失败、未知工具、参数错误和工具运行异常。
3. 提供计算器、知识检索、天气和订单四种示例工具。天气和订单数据是硬编码演示数据，不是真实外部服务；计算器未显式处理除零。
4. 读取 knowledge_base/ 下的 TXT 文件，用 BAAI/bge-small-zh-v1.5 编码文档，结合余弦相似度和 BM25 关键词分进行混合排序；返回最多 3 段证据及来源和分数。英文按词检索，连续中文拆成重叠的二/三字片段，并过滤一批通用词。
5. 文本切分优先选择句末、段落、换行等自然边界；没有合适边界时回退到空白或字符长度，并保留相邻片段重叠。
6. 用 MySQL JSON 字段保存 session_id 对应的消息历史；提供创建、列出、读取、清空和删除会话的 API。数据库按首次访问延迟连接，知识模型在首次检索时延迟加载。
7. 提供统一响应结构、输入长度校验、HTTP/参数/意外异常处理，以及记录请求方法、路径、状态码和耗时的基础日志。
8. 测试代码覆盖 Agent 工具调用/错误分支、混合检索的一些行为、文本切分、会话层伪数据库和 API 路由函数；另有 45 条检索评测样例（35 条可回答、10 条无答案）和需要真实模型服务的回答评测脚本。

知识库脚本生成的大部分材料明确标注为虚构示例。项目当前适合作为学习和演示原型；能否在某台机器上完整运行，仍取决于模型 API 配置、Python 依赖、知识文件和 MySQL 服务。本次没有做端到端确认。

四、与成熟 Agent 的差距
成熟 Agent 系统通常具备明确的流程/状态管理、运行中断与恢复、工具权限和用户授权、外部工具超时/重试/限流、流式输出、历史压缩、持久化任务状态、身份与租户隔离、审计记录、系统化离线/线上评测和部署监控。本项目目前是单进程、单 Agent 的基础工具循环，错误主要回传给模型，尚无完整运行治理能力。

RAG 方面，当前实现已超过“只有向量检索”的入门版本，但还缺少可更新的索引管线、文档元数据/版本、增量导入、权限过滤、重排、稳定结构化引用，以及规模更大且来源于真实使用场景的评测。现有 45 条样例是很好的开发起点，但检索评测用标准词在 Top-K 证据中的出现情况作为命中条件；MRR 按允许来源文件是否出现计算，不等于人工相关性判断。回答评测使用关键词包含和拒答短语匹配，只能作粗筛，不能替代人工或可靠的语义评估。

五、当前主要不足和风险（按优先级）
1. 会话访问没有身份认证/授权或用户归属校验。默认 session_id 是固定的 "default"，任何调用方都可以传入任意会话 ID；会话列表会展示所有会话。若服务对外开放，这会导致用户间会话混用或越权读取，是最优先处理的风险。
2. 会话并发一致性不足。Agent 读取整段历史、追加消息、再整段覆盖保存；同一会话并发请求可能互相覆盖。历史也没有长度限制/摘要机制，模型上下文和成本会持续增长。
3. API 错误语义有边界问题。创建会话将所有异常都包装成 409，数据库故障也可能被误报成 ID 冲突；清空不存在的会话仍返回成功。当前 API 测试主要直接调用路由函数，未覆盖真实 ASGI/HTTP 请求链路。
4. 工具仍是演示级实现。没有外部工具超时、重试、权限、审计或调用配额；订单/天气数据静态且范围有限；除零错误依赖 Agent 的通用异常捕获。真实工具扩展前需要明确失败协议和安全边界。
5. RAG 更新和质量保障不足。语料只读 TXT；文档、切分、向量和 BM25 索引均在进程内缓存，没有显式刷新/重建接口，通常需要重启才能加载新文档。没有重排、按元数据/权限过滤或稳定的 API 引用字段。向量/关键词阈值仍需在更广、真实的问题集上校准。
6. 证据输出没有穿透 API。检索工具内部返回来源及分数，但 /chat 只返回最终答案文本和 session_id；客户端无法稳定地展示引用或检查回答依据。
7. 运行可靠性与可观测性偏基础。Agent 保留 print 调试输出；日志未带请求关联 ID，缺少模型/检索/工具分段耗时、Token 用量、健康检查、限流和超时策略。README 有启动说明，但没有完整的部署/迁移/备份方案。
8. 环境复现和依赖维护可以加强。requirements.txt 固定了大量传递依赖，缺少项目专属依赖分层或标准打包配置。需要用干净环境验证安装、环境变量校验、启动和真实服务连接；README 目标 Python 版本是 3.12。
9. 仓库跟踪清单包含 sessions.db 与 logs/app.log；本次没有读取内容，因此不能判断是否含敏感信息。应确认内容安全，再决定保留跟踪还是从版本控制中移除。知识库目录未纳入 Git，克隆后不能默认得到本地语料，需提供清晰的示例数据生成步骤。
10. Agent 输入上下文没有裁剪或摘要；长对话可能超过模型上下文窗口。知识库证据也作为普通工具输出回模型，尚无专门的提示注入隔离策略。

六、建议下一步修改顺序
第一步：如果计划公开部署，先增加认证和会话所有权校验，移除共享默认会话行为，并限制会话列表访问；检查数据库和日志是否包含真实对话后再决定 Git 跟踪处理。
第二步：把项目做成可重复演示的作品：整理最小配置示例和启动步骤，在干净环境安装依赖，验证 API、LLM、MySQL 和检索链路；补一个不依赖真实密钥的 HTTP/ASGI API 测试层及必要的集成检查。
第三步：处理会话并发和增长问题，定义会话状态/写入策略、历史上限或摘要，并准确区分冲突、未找到和基础设施错误。
第四步：完善 RAG 证据体验与评估：API 返回引用来源；扩大真实风格的可回答/无答案/相似干扰样例；保存评估集版本、配置和失败案例；加入人工复核，并分别评估检索证据和最终答案。评估脚本的命中定义也应与人工相关性标注对齐。
第五步：逐步替换或扩展演示工具，补超时、可控重试、结构化错误、权限和审计；完善运行日志、请求关联、健康检查和部署配置。

如果近期目标是面试展示，优先做第一步中“会话隔离”以及第二、四步中的“干净环境可复现”和“可信评测结果”。这些比继续堆技术名词更能提升项目可信度。

二、项目目前能做什么
当前项目已经从最初的单一 Agent 原型发展为有前后端和用户体系的知识库问答应用：

1. 用户可以注册、登录，后端用 PBKDF2 保存密码哈希、JWT 做鉴权；会话按用户 ID 隔离，跨用户访问返回 404。
2. FastAPI 提供会话创建、列表、重命名、读取、清空、删除，以及同步回答和 SSE 流式聊天接口；前端可以登录、管理会话并逐步显示回答。
3. Agent 使用异步 ReAct 循环和结构化 function calling；工具参数先通过 Pydantic 校验。它有最大步数、重复工具调用守卫、工具结果截断和统一终止事件；run 与 stream 共用循环逻辑。
4. 知识库采用 Sentence Transformers 向量召回和 BM25 关键词召回，经 RRF 排序、阈值过滤后将来源和证据传给模型；检索入口提供 dense/sparse/hybrid 与门槛开关，便于做消融评测。
5. RAG 支持文档加载、三级递归切分、短块吸附、整句重叠、缓存索引；知识目录变化后可以检测并重建内存索引。
6. 记忆分为会话最近窗口、滚动摘要和跨会话长期记忆；窗口按完整对话轮裁剪，以保留 assistant 工具调用和 tool 结果配对。摘要失败时可降级继续聊天。
7. 内置计算器、天气、订单、知识检索和 remember 示例工具。工具执行、会话数据和事件流已有较完整的模块分层。
8. 测试覆盖 Agent 循环、流式事件、记忆边界、认证、会话隔离和 SSE；README/项目总结记录了 103 条检索样例和 dense/sparse/hybrid 消融评估。

四、相较成熟 Agent 的差距
项目现在具有较扎实的原型骨架，但距离成熟系统主要还差：多实例部署和持久化/可扩展索引、文档增量更新和权限过滤、重排器与可信答案评估、模型/API 超时重试和限流、并发与幂等控制、JWT 主动撤销、数据库迁移、长期记忆的用户控制、生产级监控告警和部署自动化。

它还没有覆盖复杂任务编排、长任务恢复、多 Agent 协作、人工审批和外部工具授权等企业 Agent 能力。以当前目标而言，不建议为了名词再叠 Agent 框架；优先把安全、评测和部署证据补实。

五、当前值得优先处理的问题

高优先级：

1. SSE 会将模型正文增量作为 `delta`，同时还单独生成 `thought` 事件。若这里的 thought 是模型内部推理内容，就不应直接暴露给客户端；建议只发可审计的进度说明（如“正在检索知识库”），不传原始内部推理文本。流中异常事件也直接包含异常字符串，需避免把供应商响应、内部路径或密钥相关信息返给客户端。
2. 长期记忆是由模型主动写入，但缺少清晰的用户查看/删除/关闭入口。代码里有 `forget` 逻辑，但应确认用户 API/UI 是否可以调用；在此之前，敏感信息的持久化、纠正和删除能力不足。测试好“每用户隔离”还不够，也要有明确的生命周期和同意策略。
3. 密码哈希 PBKDF2 在异步注册/登录请求路径里同步执行，计算成本较高，会占用事件循环。应将其移入线程池或使用合适的异步边界，并考虑登录限速/注册滥用防护。当前密码最小长度为 6，面向真实用户时建议提高强度要求。
4. `remember` 工具先检查记忆总数是否达到上限，再进入去重/更新逻辑；达到上限后即使是更新已有记忆也会被拒绝。应先判重并允许更新，再只对新增项应用上限。
5. 异步数据库的测试夹具通过全局环境变量临时目录设置数据库；需要留意 pytest-xdist/并行测试、不同 fixture 生命周期和连接池共享。DB 初始化与 schema 补列逻辑适合原型，团队/生产使用应转 Alembic migration。

中优先级：

6. 认证还缺少 token 撤销/刷新策略、登录失败限流、注册验证和敏感认证操作审计；JWT secret 的生产配置必须有启动时强校验，而不能沿用开发默认值。
7. 工具调用只有参数校验和通用异常处理，缺少每个工具的超时、重试预算、速率限制及明确错误类型。天气/订单仍是内存硬编码示例，不能描述成真实业务集成。
8. RAG 索引仍在单进程内存中，启动/语料变更时需要重新编码；单机演示足够，多 worker 会重复加载/计算，也无法保证索引状态一致。文档来源目前以路径/文件名为主，缺少访问控制、版本和更新记录。
9. 检索质量的已知问题是“主题相关”会误当“答案可回答”。简单 dense threshold 无法判断证据是否蕴含答案；目前评测集天花板明显，应该扩展同主题干扰文档和真实口语问题，增加答案支持/拒答的人工标注，不要继续在同一小集合上微调阈值。
10. 流式和非流式接口的错误语义不同：流开始后 HTTP 状态码无法改变，只能发送错误事件；需要确保所有错误事件最后都以单一、稳定的终止事件结束，并避免把敏感诊断内容发给客户端。为断连用户取消 LLM 请求的行为也值得确认。
11. 前端原生 JS 易部署，但还需验证 token 的存储方式、跨站脚本风险、请求错误与 SSE 中断后的恢复体验；若 token 存在 localStorage，需格外防范 XSS。
12. 本次没有运行测试，无法确认 README 中全部功能与当前代码一致或项目从干净环境可复现。依赖版本、环境变量、SQLite 默认启动和 MySQL 可选路径都应通过新环境安装验证。

六、下一步建议顺序

1. 先检查 SSE `thought` 的实际内容，改为只发送安全的进度事件；统一外部错误消息，详细异常仅写服务端日志。
2. 为长期记忆增加用户可查看、删除、关闭和纠正能力；修复已达条数上限时不能更新现有项的问题。
3. 处理认证端点的 CPU 阻塞与滥用风险：密码哈希线程化、登录限速、生产 JWT 密钥强制校验，并确定 token 撤销策略。
4. 扩建检索评测集，加入更难的同主题干扰、自然口语改写和人工判定的答案蕴含；报告配对结果和失败案例，不对当前样例做过度调参。
5. 建立干净环境的可复现启动流程和 CI：安装、迁移、API 测试、离线 Agent 测试；真实模型评测与普通 pytest 分开运行。
6. 再完善数据库迁移、限流、工具超时、索引持久化/多进程策略及部署监控。

七、总体结论
与上次评估的版本相比，项目已显著补齐认证与会话隔离、全异步架构、ReAct 循环、SSE、分层记忆和 API 测试，完成度从“单 Agent 学习原型”提高到“具备前后端闭环的 LLM 应用原型”。它适合写进简历，也有不少可供面试讨论的工程取舍。

目前最需要避免的是把“功能多”误当成“已生产化”：流式推理暴露、记忆治理、认证滥用防护和 RAG 答案可支持性仍需要优先处理；项目的检索提升尚未被现有评测充分证明。本次仅做代码阅读，没有改动源码，也没有运行验证。

具体问题，按优先级排列

P1：同步 SSE 生成器中的 ContextVar 作用域跨越 yield，可能使正常回答缺失 done 事件。
位置：api/chat_helpers.py:44、tools/knowledge.py:47。
chat_event_stream 在 knowledge_owner_scope 中 yield delta；scope 进入时保存 ContextVar token，退出时 reset。当前本地安装的 Starlette iterate_in_threadpool 对每次 next 使用一次 anyio.to_thread.run_sync，AnyIO 为调用复制 context。生成器再次恢复时，reset 可能在不同 Context 中执行并抛 ValueError；外层捕获后发 error，正常 done 不再发送。即使线程相同，也不代表 Context 相同。
这项判断基于项目及本地依赖源码，尚未执行请求复现。建议优先用真实 ASGI StreamingResponse 验证，并把用户范围改为显式参数，或让 set/reset 完成于同一次 next 内，避免上下文管理器跨 yield。不能靠直接 list(generator) 证明真实 HTTP 路径正常，也不能据此断言已发生跨用户泄露。

P1：引用数据在真实工具链中被双重编码，接口和历史页无法按预期读取。
位置：tools/knowledge.py:343、agent/agent.py:244、api/chat_helpers.py:7、frontend/src/App.tsx:164。
knowledge_search_context 返回 json.dumps 后的字符串；Agent 再对这个字符串 json.dumps。latest_turn_citations 只 json.loads 一次，得到字符串而非字典，然后在 isinstance 判断处跳过。前端历史页也只解析一次。因此标准 knowledge_search_context 调用即使检索成功，正常完成时 citations 也会为空。
现有 HTTP 测试直接伪造单层 JSON 工具消息，未走实际工具返回和 Agent 序列化，覆盖不到这个问题。建议统一工具返回 Python dict，协议边界只序列化一次，并增加“真实上下文工具 + 模拟模型 + HTTP”的链路用例。

P1：文档上传和替换在 async 路由中直接执行同步解析、磁盘读写及数据库事务。
位置：api/routes/documents.py:64、96，services/documents.py:72。
await file.read 后直接调用同步服务。复杂 PDF/Office 解析或数据库等待会阻塞事件循环，拖慢同一进程中其他请求。建议把整段同步服务放到受限线程池，较大文件使用后台任务和状态查询。20 MB 上传限制只限制压缩文件体积，不限制解压大小、页数、单元格数或解析耗时，还应设解析资源预算。

P1：文档文件操作与数据库事务缺少一致性保障。
位置：services/documents.py:139、164、187。
替换同名文件时 _parse_and_save 直接覆盖旧路径；之后数据库提交失败，旧文件已经改变，数据库回滚无法恢复。改名在事务提交前移动文件，也有同样问题。删除先提交数据库，再删文件；若磁盘删除失败，记录已不存在，解析文本可能仍被扫描检索，且刷新缓存不会执行。
检索只扫描目录，不核对有效数据库记录，使残留文件具有实际影响。建议采用版本化新文件、临时写入、数据库指针切换、失败补偿和可重试清理；检索依据已发布的文档版本构建索引。SQL 事务不能回滚文件系统操作。

P2：SSE 存在，但当前不是低延迟增量输出。
位置：agent/agent.py:156、175、229、236。
模型开启 stream=True 后，所有正文先追加到 content_parts；直到该轮完全结束、确认没有工具调用并过滤标签，才 yield 一次完整 public_answer。用户仍需等待完整答案，README 所说的逐段输出不符合该实现。
可以明确选择“完整答案审核后输出”的模式，或重新设计最终回答阶段与增量过滤，在确保公开正文边界后逐段发送。不能只把 stream=True 或 SSE 响应头当作已实现逐字输出的证明。

P2：同会话并发仍会丢失消息，历史也没有预算。
位置：agent/agent.py:43、156，agent/session.py:35。
两个请求可读到同一份历史，再分别保存整段 JSON，后写入的一方覆盖另一方。清空/删除与生成并发也可能导致历史重现，save 会自动创建不存在的会话。前端禁用发送不能限制多标签页或直接 API 请求。
建议引入会话运行状态、版本校验或串行队列，避免把数据库锁持有到整个模型调用结束；增加完整工具消息组的上下文裁剪和必要的摘要。当前没有三层记忆，不能在简历里写已实现。

P2：前端并发刷新 token 存在竞态。
位置：frontend/src/api.ts:278；frontend/src/App.tsx 中登录后并行加载会话与文档列表。
多个请求遇到 401 时，各自用同一个 refresh token 调刷新。后端只允许一次成功；另一请求失败后会删除 sessionStorage 中的 token，可能清掉刚刚保存的新令牌，造成随机掉登录。应共用一个刷新 Promise，其他请求等待它完成后重试，并校验失败请求是否仍对应当前令牌。

P2：索引刷新只清当前进程，而且多份缓存不构成同一版本快照。
位置：tools/knowledge.py:66、109、155、391。
文本、向量、BM25 分别缓存，上传清理三份缓存。多 worker 下其他进程不会收到更新；单进程并发更新时，某次检索也可能持有旧文本、却取得新向量或关键词索引，出现结果错位或索引错误。公共语料还会按用户重复编码和缓存。
建议用文档版本或索引版本统一失效，构建不可变索引快照后整体切换；公共索引与个人索引分离。没有规模压力时不必立即引入外部向量数据库，但需先保证版本一致。

P2：历史引用没有绑定到各自回答。
位置：frontend/src/App.tsx:164。
displayMessages 将整段历史的所有工具引用收集到一个数组，全部附给最后一条 assistant 消息。即便修复双重编码，重开多轮会话仍会把早期引用展示在最新答案下。建议保存 turn_id/message_id 与引用关系；至少按 user 边界分组恢复。

其他具体改进

创建会话仍捕获所有异常并返回 409，数据库故障会被误报为重复 ID（api/routes/sessions.py）。run 和 run_stream 各有一套循环；前者直接返回原始 message.content，后者做 _public_answer 过滤，维护时已有行为差异。建议统一执行策略与工具结果协议。

上传文档解析是文本提取，不包含扫描 PDF 的 OCR、完整版式恢复和精确页码引用；PPTX 当前只遍历有文本框的 shape，不能当作完整表格/图片解析。文件来源只是显示名称，缺少稳定 document_id、页码/工作表/片段 ID，不利于核验来源。前端把综合相关分显示成百分比，容易让用户误解为正确概率，建议明确标成相关度。

无证据拒答目前仍依赖工具返回标记与系统提示词，tool_choice 为 auto；不能保证每次必须检索，也不能保证有检索结果就有答案依据。需要覆盖模型跳过检索、证据相关但无答案、文档内恶意指令等情况。

README 对旧表迁移/归属回填的描述互相冲突：配置章节描述回填，后文又说不自动迁移；当前 initialize_database 仅 create_all。应以迁移脚本和当前实现为准。依赖清单包含大量固定的传递依赖，建议清晰区分直接依赖和锁文件，记录验证过的 Python 环境。

测试与评测应怎样补

已有单元测试和 ASGI 测试是基础，但 Mock 边界过宽会让组件分别通过、组合后失败。优先补真实工具序列化到 SSE 引用的测试、跨线程 SSE ContextVar 作用域、文档替换/改名/删除失败补偿、用户 A/B 上传检索隔离、并发刷新 token 和同会话并发。无需先追求测试条数。

当前 hit_rate 是“允许来源的 Top-K 文本拼接后覆盖全部标准词”的问题命中率；MRR 只要求允许的来源文件出现，未必命中该文件的正确片段。它们不能等同于最终答案准确率或严格的证据级 Recall。报告虽有问题集指纹，还应记录语料版本、代码提交、模型版本与运行环境，增加独立留出集和人工证据支持性标注。本次没有复测任何历史指标。
